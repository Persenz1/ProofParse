# 模型重新选型与开发计划（2026-09-30）

> **说明**：本文写于重构之前。候选模型名单及选择依据仍然有效；执行顺序与工程安排以 [开发计划](DEVELOPMENT_PLAN.md) 为准。文中所说的“接入现有公式识别或 parser 接口”，现在指 `proofparse/engines/` 下的适配器；测试文件放在 `output/` 下的约定不变。旧测试报告已移到 [history/](history/)。

本轮保留现有流水线：前处理 → 版面与区域定位 → 文字、公式及表格识别 → 候选比较与必要修正 → 按源位置归位 → Markdown 与图片交付。重点更换或补充能力不足的模型，不重建整套流程。

本文记录已讨论的选型建议与下一轮工作安排。候选能力依据截至 2026-09-30 查阅的官方资料；新增模型尚未在项目样本上实测，测试优先级不等于最终准确率排名。本次仅归档计划，未安装依赖、下载权重、调用新模型或修改解析代码。

## 当前基础与具体短板

- 当前默认使用 MinerU pipeline；本机已安装版本的版面模型为 PP-DocLayoutV2，公式第一路为 UniMERNet small，ProofParse 第二路为 PP-FormulaNet plus-M。它们已经是现有基线，不作为全新候选重复建设。
- plus-M/L 已在相同 22 个公式区域上完成试验。L 改善部分矩阵，但仍会出现多余字符、分组或字体错误，暂不全量替换 M。已测 M 推理 4.630 秒、L 推理 20.837 秒；后端和批量不同，不能视为纯模型速度比较。详见[公式测试报告](history/FORMULA_EVALUATION_2026-09-30.md)。
- t21/t22 的裁图夹入相邻行，t22 还包含正文。需要把区域边界改进与公式识别改进分开测试；换公式模型不能恢复裁掉的内容，也不能保证排除混入内容。
- 后续复核已确认 t20 源 PDF 本身缺右括号，应忠实保留，不能继续把该项计为 L 漏识。以[后续复核说明](history/FORMULA_VERIFIER_2026-09-30.md)为准。
- 其他现有问题包括代码误分类、图外标注裁切、行内公式定位及重复片段的唯一写回。模型改进可减少上游错误，但源坐标关联和精确写回仍由程序处理。

## 候选优先级与接入位置

| 候选 | 安排 | 主要用途与判断依据 |
|---|---|---|
| Xiaomi-OCR-0 | 第一批，重点测试 | 新增公式区域识别候选；同时支持区域和整页输入，具有直接的单公式评测证据 |
| PaddleOCR-VL-1.6 | 第一批，优先接入 | 明确提供公式识别接口；完整方案采用版面检测后分区域识别，适合现有流程 |
| OvisOCR2 | 第一批强对照 | 比较纯公式裁图与含上下文段落；官方主定位是整页 Markdown，局部裁图效果需单独验证 |
| MinerU2.5-Pro | 第一批底座对照 | 与当前 MinerU pipeline 比较整页提取、区域分类、公式及图文关联 |
| PP-DocLayoutV3 | 第一批版面对照 | 与现有 V2 比较区域定位；它也是 Paddle、GLM、Xiaomi 相关方案的版面组件 |
| TeleOCR | 第一批版面对照，按需测公式 | 提供版面、公式和代码等任务接口，重点覆盖代码误分类、区域划分与复杂页面 |
| GLM-OCR | 第二批或部署替补 | 提供另一种模型的公式候选；是否优于首批候选需本地测试 |
| PP-FormulaNet plus-M | 保留快速基线 | 已跑通，作为常规公式及速度对照 |
| PP-FormulaNet plus-L | 保留困难公式补识别 | 复用已有权重与结果，测试它能否补足新组合仍未解决的项目 |
| UniMERNet | 保留现有 small，base 后置 | small 已在使用；base 属于同系列扩容，优先级低于新的 OCR 专用 VLM |
| pix2tex / LaTeX-OCR | 暂缓 | 需要历史基线比较时再加入，暂不占用首轮工程投入 |

最终默认组合按实测收益收敛，不让全部候选常驻或对每条公式全部运行。

## 公开结果如何支持选择

下表统一摘自 [Xiaomi-OCR-0 技术报告表 1](https://arxiv.org/html/2609.36136v1)中的 OmniDocBench v1.6 比较。属于该报告列示的公开结果，不是本项目复测；Formula CDM 不能解释为整条公式完全正确率。

| 模型 | Formula CDM ↑ |
|---|---:|
| Xiaomi-OCR-0 | 98.50 |
| OvisOCR2 | 97.53 |
| PaddleOCR-VL-1.6 | 97.49 |
| MinerU2.5-Pro | 97.45 |
| GLM-OCR | 97.18 |
| TeleOCR | 96.36 |

Xiaomi 另报告 UniMER-Test 单公式测试 Overall 97.84。其主要整页成绩采用 PP-DocLayoutV3 检测、裁图识别和页面拼装，0.8B 参数不包含外部版面检测器。因此，它值得在当前分阶段流程中测试，不必先改成整页单模型输出。详见[技术报告的推理设置和元素识别部分](https://arxiv.org/html/2609.36136v1)。

PaddleOCR-VL-1.6 和 GLM-OCR 都明确提供 `Formula Recognition:` 任务接口；优先用它们独立生成 LaTeX 候选，不能把 OCR 分数解释成可靠的校核能力。[Paddle 模型说明](https://huggingface.co/PaddlePaddle/PaddleOCR-VL-1.6)、[GLM 模型说明](https://huggingface.co/zai-org/GLM-OCR)。

OvisOCR2 的官方默认输入为整页，输出包含公式、表格和图片区域坐标的 Markdown；小公式裁图和含行内数学段落应分别测试。[OvisOCR2 模型说明](https://huggingface.co/ATH-MaaS/OvisOCR2)。

TeleOCR 提供版面分析、单公式和代码识别接口。整页总分较高不代表其公式分项最优，首轮主要检验它对当前定位与分类问题的帮助。[TeleOCR 模型说明](https://huggingface.co/XingChen-AGI/TeleOCR)。

MinerU 工具版本与 VLM 权重版本需要分开记录。现有 MinerU 3.4.5 的 pipeline 不等于已经使用 MinerU2.5-Pro；新增对照采用明确的 Pro 权重及对应接口，例如 [MinerU2.5-Pro-2604-1.2B](https://huggingface.co/opendatalab/MinerU2.5-Pro-2604-1.2B)，不能只记录“MinerU”。

## 下一轮工作顺序

### 1. 固定公式区域，比较识别能力

复用现有 22 条公式及已保存的 UniMERNet、M/L 候选，新增 Xiaomi、PaddleOCR-VL-1.6、OvisOCR2。保持源区域一致，各模型使用自己的官方预处理和任务提示词；保存实际分辨率、输出长度限制、精度、批量及后端等必要复现参数。

各模型先独立转录，不先展示其他模型答案。比较完整公式的符号、上下标归属、矩阵行列和字体，而不只统计此前某一个错误点是否被修好。已有金标准由代理复核，不写成人工确认；采用明确的等价 LaTeX 表达，编号在裁图外时单独关联。

t21/t22 额外比较原裁图与清理边界后的裁图，保留两组结果。OvisOCR2 另测含上下文的段落输入，以判断它适合充当局部识别器还是段落级补充。记录完整修复量、新增错误、残留未解决项及耗时，识别各模型的真实互补性。

### 2. 固定源页面，比较版面与解析底座

选用上述难例所在页，以及已有代码误分类、图外标注裁切等问题页；不先重解析全部论文。

- 比较当前 MinerU pipeline 与 MinerU2.5-Pro 的完整输出。
- 比较 PP-DocLayoutV2、V3 和 TeleOCR 对问题区域的定位与分类；可复用候选官方管线，先避免为测试建设通用后端框架。
- 分别看公式是否漏检、正文是否混入、代码是否误当公式、图片及标注是否完整、阅读顺序和图注关联是否正确。
- 只有在相同裁图下的收益才归入识别器改进；重新定位带来的收益归入区域或底座改进。大块版面改善不代表行内公式细边界已解决。

### 3. 选出小组合，接入一次完整修正流程

根据前两步结果选择主识别器和有实际互补收益的补充模型，保留现有快速基线。默认采用“独立识别 → 比较候选 → 对冲突定向复核”，不把多个相同答案直接当成正确，也不把 M/L 视为完全独立的证据。

接入现有公式识别或 parser 接口，继续复用稳定对象 ID、源坐标、编号关联、图片资源和现有写回逻辑。公式任务应产生可用的完整 LaTeX，必要时产生精确边界修正；程序负责归位及 Markdown 定界符。

在这批样例上实际完成一次识别、修正、写回与核对，观察最终错误、未解决项及 agent 接手量。初步选出组合后，再用少量未参与调试的新页确认收益。以最终转录结果评价组合，不以模型返回 `match`、LaTeX 可编译或候选一致作为内容正确的替代指标。

## 本机运行安排

现有环境为 Windows、RTX 4060 Ti 8GB。优先按模型或阶段集中小批推理，用完卸载，避免多个 VLM 同时占用显存。参数量不能替代实际显存测量，官方服务端示例也不代表本机已验证可用。

复用已有 M/L 权重和运行环境。此前同进程混用 Paddle 与 PyTorch 出现过 cuDNN 冲突，新候选按需要隔离运行进程和依赖，不覆盖已跑通的环境。首次质量比较优先采用官方推荐精度；若因显存需要量化，明确记录，并与未量化结果分开比较。

测试工作副本、裁图和过程文件放在仓库 `output/` 的专属子目录；不改源 PDF 或已有基线结果。完成比较后只整理有用的模型结果、运行参数和简短结论，不另外建立重复的审计材料。本文归档不自动启动下载、安装或付费测试。
